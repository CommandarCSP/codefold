# 성능 보고서

ZIP 에디터의 성능 목표를 실제 브라우저에서 잰 결과입니다. 목표는 [ADR-0027](adr/0027-performance-budgets.md)에서 정했고, 이 문서는 스펙 Task 20에 해당합니다.

## 요약

| 지표 | 목표 | 개발 기기 | CI 기준 환경 | 판정 |
|---|---|---|---|---|
| 첫 화면 JS 크기 | gzip 150KB 이하 | 131.5KB | 131.5KB | 통과 |
| 키 입력당 React 렌더 | 0회 (수정 여부가 바뀔 때만 1회) | 첫 글자 1회, 나머지 99글자 0회 | 같음 | 통과 |
| 입력 중 50ms를 넘는 긴 작업 | 0건 | 0건 | 0건 | 통과 |
| 파일 1만 개 ZIP의 트리 표시 | 업로드 후 1초 이내 | 0.50초 | 0.73초 | 통과 |
| 파일 1만 개 ZIP 다운로드 | 목표 없음 (기록만) | 3.1초 | 11.6초 | 개선 후보 |
| Monaco·언어별 청크 크기 | 목표 없음 (기록만) | Monaco 본체 683KB, TS 언어 Worker 1,457KB (gzip) | 기록 |

목표를 정한 네 지표는 개발 기기와 CI 기준 환경 모두에서 통과했습니다. 시간은 모두 5회 중앙값입니다. 목표가 없는 다운로드 시간은 파일 수에 비례해 늘어나서, [개선 후보](#발견한-점과-개선-후보)로 적었습니다.

## 측정 환경과 다시 재는 방법

같은 항목을 두 곳에서 잽니다. 개발 기기에서는 명령 하나로 다시 잴 수 있고, CI는 `main`에 push할 때마다 잽니다.

| 항목 | 값 |
|---|---|
| 기기 | 개발 기기: Apple M2 Pro (12코어), 메모리 16GB, macOS (Darwin 25.5.0). CI 기준 환경: GitHub Actions `ubuntu-latest` (Intel Xeon 2코어, 메모리 8GB, Node 24) |
| 브라우저 | Playwright 1.63의 Chromium |
| 앱 | 운영 빌드(`vite build`)를 로컬 미리보기 서버(`vite preview`)로 띄운 것 |
| 측정일 | 개발 기기 2026-09-28, CI 2026-09-29 (`e201a41`) |
| 반복 | 시간 지표는 새 브라우저 컨텍스트에서 5회씩 재고 중앙값을 씁니다. |

```bash
pnpm --filter @codefold/zip-editor perf
```

- 이 명령은 앱을 빌드한 뒤 `apps/zip-editor/perf/perf.spec.ts`를 Chromium에서 차례로 실행하고, 청크 크기를 잽니다.
- 결과는 `apps/zip-editor/perf-results/`의 `results.json`과 `chunks.json`에 남습니다. 이 폴더는 커밋하지 않습니다.
- 반복 횟수는 `PERF_RUNS`, 미리보기 서버 포트는 `PERF_PORT`(기본 4174)로 바꿉니다.
- 로컬 서버에서 재므로 네트워크로 받는 시간은 거의 0입니다. 실제 사용자의 첫 방문에서는 에디터 청크를 받는 시간이 더 듭니다.

## 항목별 결과

### 1. 첫 화면 JS 크기

| 항목 | 내용 |
|---|---|
| 목표 | gzip 150KB 이하. Monaco와 dockview는 첫 화면에 넣지 않습니다. |
| 재는 방법 | 빌드 결과의 엔트리와 그 정적 import만 gzip으로 압축해 더합니다(`scripts/check-bundle.mjs`). 첫 화면 청크에 Monaco나 dockview 코드가 들어 있으면 실패합니다. |
| 결과 | **131.5KB** (`index-*.js` 한 파일) |
| CI | 넘으면 실패합니다. |
| 근거 | [ADR-0027](adr/0027-performance-budgets.md), [ADR-0021](adr/0021-monaco-direct-without-wrapper.md) |

첫 화면에는 업로드 영역만 있습니다. 에디터 코드는 ZIP을 열기 시작할 때 받아 옵니다.

### 2. 키 입력당 React 렌더

| 항목 | 내용 |
|---|---|
| 목표 | 키 입력마다 0회. 파일이 처음 수정될 때처럼 수정 여부가 바뀔 때만 1회입니다. |
| 재는 방법 | 페이지에 React 개발자 도구가 쓰는 훅 대신 가짜 훅을 심어, React가 화면을 바꿔 그릴 때마다(커밋) 그 횟수를 셉니다. 300줄짜리 TS 파일을 열고 첫 글자를 입력한 뒤, 나머지 99글자를 빠르게 입력합니다. |
| 결과 | **첫 글자 1회, 나머지 99글자 0회** |
| CI | CI 성능 작업이 잽니다. 99글자 동안 커밋이 1회라도 나오면 실패합니다. 첫 글자에서 커밋이 없어도 실패합니다. 첫 글자에서는 반드시 커밋이 1회 나와야 하므로, 없으면 측정 훅이 작동하지 않은 것입니다([ADR-0045](adr/0045-render-count-via-devtools-hook.md)). |
| 근거 | [ADR-0006](adr/0006-monaco-model-as-content-source.md), [ADR-0019](adr/0019-react-compiler.md) |

첫 글자에서 1회 그리는 것은 파일이 "수정됨"으로 바뀌어 트리·탭의 표시가 바뀌기 때문입니다. 그다음부터는 수정 여부가 그대로라서 React가 전혀 다시 그리지 않습니다. 파일 내용은 Monaco model에만 두고, `monaco-binding`은 수정 여부가 바뀔 때만 알림을 보내도록 설계했기 때문입니다.

### 3. 입력 중 긴 작업과 입력 응답

| 항목 | 내용 |
|---|---|
| 목표 | 입력 중 50ms를 넘는 작업 0건 |
| 재는 방법 | 위 2번과 같은 100글자 입력 동안, Long Tasks API로 50ms를 넘는 작업을 모으고, Event Timing API로 16ms를 넘게 걸린 입력 처리를 모읍니다. |
| 결과 | **긴 작업 0건.** 가장 오래 걸린 입력 처리는 24ms입니다. CI 기준 환경에서도 긴 작업은 0건이고, 가장 오래 걸린 입력 처리는 48ms입니다. |
| CI | 시간 지표라서 실패시키지 않고, 기록한 뒤 긴 작업이 1건이라도 있으면 경고합니다. |
| 근거 | [ADR-0027](adr/0027-performance-budgets.md) |

입력에 100ms 안에 반응이 오면 사람은 즉각적이라고 느낍니다(RAIL 모델). 가장 느린 입력 처리도 24ms이고, 더 느린 CI 기준 환경에서도 48ms라서 여유가 있습니다.

### 4. 파일 1만 개 ZIP의 트리 표시

| 항목 | 내용 |
|---|---|
| 목표 | 업로드 후 1초 이내 |
| 재는 방법 | 파일 1만 개(폴더 100개)가 든 ZIP을 파일 선택으로 업로드합니다. 파일을 고른 순간부터 트리의 첫 줄이 화면에 생길 때까지를 잽니다. 앱 안의 측정 구간(`codefold:zip-open` → `codefold:tree-ready`)도 함께 읽습니다. |
| 결과 | **0.50초** (5회 중앙값, 0.48~0.51초). 앱 안 측정은 0.49초. CI 기준 환경: **0.73초** (0.69~0.73초) |
| 더 많은 파일 | 파일 5만 개: 0.59초 (0.57~0.59초). CI 기준 환경: 0.86초 (0.84~0.92초) |
| CI | 시간 지표라서 실패시키지 않고, 기록한 뒤 1초를 넘으면 경고합니다. |
| 근거 | [ADR-0001](adr/0001-zip-parser-in-house.md), [ADR-0028](adr/0028-zip-work-in-web-worker.md), [ADR-0029](adr/0029-virtualized-file-tree.md) |

파일이 5배로 늘어도 0.09초만 늘었습니다. 시간 대부분은 파일 수와 상관없이 드는 준비 시간으로 보입니다(에디터 청크 불러오기, Worker 시작 등. 나눠서 재지는 않았습니다). 파일 수가 늘어도 시간이 거의 늘지 않는 까닭은 ZIP 끝의 목차만 읽고, 트리는 화면에 보이는 줄만 그리기 때문입니다.

### 5. 파일 1만 개 ZIP 다운로드 (추가 지표)

| 항목 | 내용 |
|---|---|
| 목표 | 없음. ADR-0027에 없는 지표라 기록만 합니다. |
| 재는 방법 | ZIP을 업로드하고 파일 하나를 수정한 뒤, 다운로드 버튼을 누른 순간부터 브라우저가 다운로드를 시작할 때까지를 잽니다. |
| 결과 | 파일 100개: **0.06초**. 파일 1만 개: **3.1초** (2.6~3.6초). CI 기준 환경: 파일 100개 0.25초, 파일 1만 개 **11.6초** (11.2~12.3초) |

파일 수가 100배가 되자 시간은 약 50배가 됐습니다. 파일 하나에 약 0.3ms가 드는 셈입니다. 추정한 원인은 아래 [개선 후보](#발견한-점과-개선-후보)에 적었습니다.

### 6. 청크 크기 (기록만)

첫 화면 청크와, ZIP을 연 뒤 필요할 때 받는 청크를 함께 적었습니다. 첫 화면 청크를 뺀 나머지는 첫 화면 크기에 들어가지 않습니다.

| 청크 | gzip | 언제 받나 |
|---|---|---|
| 첫 화면 (`index-*.js`) | 131.5KB | 처음 방문할 때 |
| 에디터 영역 (`EditorHost-*.js`, dockview 포함) | 120.3KB | ZIP을 열기 시작할 때 |
| Monaco 본체 (`editor.api-*.js`) | 683.1KB | ZIP을 열기 시작할 때 |
| 기본 에디터 Worker (`editor.worker`) | 90.7KB | 에디터를 처음 띄울 때 |
| ZIP Worker (`zip.worker`) | 5.3KB | ZIP을 열 때 |
| TS·JS 언어 Worker (`ts.worker`) | 1,456.6KB | TS·JS 파일을 처음 열 때 |
| CSS 언어 Worker (`css.worker`) | 240.7KB | CSS 파일을 처음 열 때 |
| HTML 언어 Worker (`html.worker`) | 191.5KB | HTML 파일을 처음 열 때 |
| JSON 언어 Worker (`json.worker`) | 125.5KB | JSON 파일을 처음 열 때 |
| 문법 강조 규칙 (예: `python-*.js`, `typescript-*.js`) | 1~2KB씩 | 그 언어의 파일을 처음 열 때 |

JS 파일 전체를 더하면 gzip 3.5MB지만, 한 사용자가 한 번에 받는 양은 여는 파일의 언어에 따라 다릅니다. 가장 큰 것은 TypeScript 언어 기능이 든 `ts.worker`로, TS·JS 파일의 자동 완성과 오류 표시에 씁니다. 이 파일은 TS·JS 파일을 열 때만 받습니다([ADR-0026](adr/0026-monaco-language-loading.md)).

## 발견한 점과 개선 후보

**파일이 많은 ZIP의 다운로드가 파일 수에 비례해 느려집니다.** 파일 1만 개에 개발 기기에서 약 3초, 2코어인 CI 기준 환경에서 약 12초가 걸립니다. 이 비율이면 5만 개에는 개발 기기에서도 15초쯤 걸릴 것으로 보입니다.

- **원인 (코드를 읽고 한 추정)**: 수정하지 않은 파일은 원본의 압축 데이터를 그대로 옮기는데, 그 데이터가 어디서 시작하는지 알려면 파일마다 로컬 헤더(30바이트)를 읽어야 합니다(`packages/zip-archive/src/entry-data.ts`의 `readRaw` → `dataRange`). 앱의 Worker는 이 읽기를 파일마다 하나씩 차례로 기다립니다(`apps/zip-editor/src/services/zip/zipWorkerHandler.ts`). 파일 1만 개면 작은 읽기가 1만 번 이어집니다.
- **고치는 방법 후보**
  - 로컬 헤더 읽기를 여러 개씩 동시에 합니다.
  - 이어진 여러 파일에 걸친 구간을 한 번에 크게 읽고, 그 안의 로컬 헤더를 한꺼번에 해석합니다.
- 이 추정은 아직 측정으로 확인하지 않았습니다. 고치기 전에 읽기 시간만 따로 재서 확인합니다.

## 한계

- **CI 값은 실행마다 조금씩 다릅니다.** CI 러너의 속도가 실행마다 달라서, 시간 지표가 목표를 넘어도 CI를 실패시키지 않고 경고와 실행 요약 표로만 남깁니다([ADR-0027](adr/0027-performance-budgets.md)). 이 보고서의 CI 값은 한 번 실행한 결과입니다. 실행별 값은 그 CI 실행의 `perf-results` 산출물(artifact)에 남습니다.
- **네트워크 시간이 빠져 있습니다.** 로컬 서버에서 쟀으므로, 느린 네트워크에서 에디터 청크를 처음 받는 시간은 들어 있지 않습니다.
- **Chromium에서만 쟀습니다.** Long Tasks API를 Chromium만 지원하기 때문입니다.
