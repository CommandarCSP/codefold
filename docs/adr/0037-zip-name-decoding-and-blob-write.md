# ADR-0037. ZIP 이름은 유니코드 경로 확장 필드도 읽고, 새 ZIP은 조각을 이어 붙인 Blob으로 만든다

- 상태: 승인
- 날짜: 2026-09-27
- 일부 대체: ADR-0001의 파일 이름 읽는 순서, ADR-0016의 "`writeZip`은 스트림으로 쓴다"

## 배경

`@codefold/zip-archive`를 구현하면서 두 가지가 ADR-0001·ADR-0016과 달라졌다.

1. **파일 이름 읽는 순서.** ADR-0001은 "UTF-8 플래그 → 엄격한 UTF-8 → CP949 → CP437" 순서로 이름을 읽는다고 정했다. 그런데 Info-ZIP 같은 일부 도구는 옛 인코딩(CP949 등)으로 이름을 적으면서 같은 이름의 UTF-8 판을 **유니코드 경로 확장 필드**(ID `0x7075`)에 따로 적어 둔다. 이 필드를 읽지 않으면 올바른 UTF-8 이름이 있는데도 CP949나 CP437로 추측해야 한다.
2. **새 ZIP을 쓰는 방식.** ADR-0016은 `writeZip`이 "스트림으로 쓴다"고 적었다. 실제로는 결과를 `Blob` 하나로 돌려주기만 하면 되고(ADR-0028의 `exportZip`), 원본 압축 바이트는 `Blob.slice()` 조각이라 복사하지 않고 이어 붙일 수 있다.

## 결정

### 이름 읽는 순서

다음 순서로 시도하고, 처음 성공한 방법을 쓴다. 결과는 NFC로 바꾼다.

1. UTF-8 플래그(general purpose bit 11)가 켜져 있으면 UTF-8
2. 유니코드 경로 확장 필드(`0x7075`)가 있고, 그 필드에 적힌 CRC-32가 헤더에 적힌 이름 바이트의 CRC-32와 같으면 그 UTF-8 이름
3. 엄격한 UTF-8로 읽히면 UTF-8
4. CP949 바이트 짝 규칙에 맞고 CP949로 읽히면 CP949
5. 나머지는 CP437

2단계에서 CRC를 확인한다. 이름을 나중에 바꾼 ZIP에서는 확장 필드가 옛 이름을 가리키기 때문이다.

### 새 ZIP 쓰기

`writeZip(items)`는 항목마다 로컬 헤더와 데이터를 만들고, 끝에 목차와 EOCD를 붙여 **조각을 이어 붙인 `Blob` 하나**로 돌려준다.

- `raw` 항목(원본 복사)의 데이터는 원본 ZIP의 `Blob.slice()` 조각이다. 메모리로 복사하지 않는다.
- `file` 항목(새 내용)은 `CompressionStream('deflate-raw')`로 파일 하나씩 압축해 메모리에 둔다. 압축해도 줄지 않으면 Stored로 쓴다.
- 결과 전체를 스트림으로 내보내지는 않는다.

## 근거

- 유니코드 경로 확장 필드는 ZIP을 만든 도구가 직접 적은 UTF-8 이름이라, 인코딩을 추측하는 것보다 정확하다. CRC 확인으로 낡은 필드를 거른다.
- 결과를 `Blob` 하나로 주면 Worker에서 메인 스레드로 넘기기 쉽고(ADR-0028), 다운로드 링크를 바로 만들 수 있다. `Blob`은 조각을 참조만 하므로 안 고친 파일의 원본 바이트는 복사되지 않는다.
- 끝까지 스트림으로 쓰면 브라우저 파일 저장 API(`showSaveFilePicker` 등)가 필요한데, 지원 브라우저(ADR-0030) 가운데 이 API를 못 쓰는 것이 있다.

## 결과

- 이름 읽는 순서에 유니코드 경로 확장 필드 단계가 들어간다.
- ZIP은 스트림이 아니라 조각을 이어 붙인 `Blob`으로 만든다.
- 새로 쓰는 파일은 압축 전 바이트와 압축본이 잠시 함께 메모리에 있다. 고친 파일이 아주 크면 다운로드할 때 메모리를 많이 쓴다. zip-archive README의 "메모리를 생각합니다"에 적는다.
