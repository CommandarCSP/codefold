# ADR-0007. 에디터 영역에 dockview로 분할·플로팅 도킹을 넣는다

- 상태: 승인 (같은 창 안의 플로팅 그룹은 ADR-0042로 일부 대체)
- 날짜: 2026-09-27

## 배경

코드 에디터에서 두 파일을 나란히 보거나 한 파일을 잠시 띄워 두는 일은 흔하다. 탭을 끌어서 에디터 영역을 나누거나 떠 있는 창으로 띄우는 도킹 UI를 검토했다.

제약은 두 가지다.

- 기본 레이아웃은 상단 업로드/다운로드, 왼쪽 파일 트리, 오른쪽 탭 + 에디터다. 사용자에게 익숙한 코드 에디터(VS Code 등)의 배치이고, 업로드·다운로드 버튼과 파일 트리는 화면을 나눠도 늘 같은 자리에 있어야 찾기 쉽다.
- ADR-0006은 에디터 인스턴스를 하나로 두고 model만 갈아 끼우는 구조를 정했다.

## 선택지

도킹을 넣을지, 넣는다면 어디까지 어떤 라이브러리로 할지 네 가지를 비교했다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 도킹 없이 탭 + 에디터 하나 | 가장 단순하다 | 두 파일을 동시에 볼 수 없다 |
| B. dockview를 에디터 영역에만 적용 | 분할·플로팅·팝아웃을 지원하고 의존성이 없다. React를 지원한다. 기본 레이아웃을 유지할 수 있다 | 탭·레이아웃 상태를 dockview가 소유한다. 그룹 수만큼 에디터가 생긴다 |
| C. 화면 전체를 도킹으로 구성 | 트리·업로드 바까지 자유롭게 배치할 수 있다 | 기본 레이아웃이 흐트러질 수 있다 |
| D. FlexLayout, rc-dock, golden-layout | 기능이 비슷하다 | TypeScript 지원과 유지보수가 얼마나 활발한지를 따지면 dockview보다 불리하다 |

## 결정

**B를 택한다.**

- dockview는 **오른쪽 에디터 영역 안에서만** 쓴다. 업로드 바와 파일 트리는 고정 레이아웃이다.
- 처음 화면은 탭 줄 하나와 에디터 하나로 보인다.
- 지원 기능: 탭 끌어 놓기로 **분할**(좌우·위아래), 같은 창 안의 **플로팅** 그룹.
- **팝아웃(별도 브라우저 창)은 구현 초반에 짧게 시험한 뒤 결정한다.** Monaco는 CSS를 메인 문서에 주입하고 포커스·키보드 처리를 메인 창 기준으로 하므로 별도 창에서 스타일이나 입력이 깨질 수 있다. 시험 결과는 새 ADR로 남긴다.

### ADR-0006과의 관계

- 에디터 인스턴스는 "앱 전체에 하나"에서 "**보이는 그룹마다 하나**"로 바뀐다. 그룹 안에서 탭을 바꿀 때는 여전히 에디터를 다시 만들지 않고 model만 갈아 끼운다.
- model은 그대로 **파일마다 하나**다. 같은 파일을 두 그룹에 띄우면 두 에디터가 같은 model을 공유해, 입력과 undo 기록이 양쪽에 함께 반영된다.

### 상태 소유권

- **열린 탭, 탭 순서, 그룹 배치, 활성 탭**의 주인은 dockview다. 앱은 이 상태를 dockview API와 이벤트로 읽고 조작한다.
- **파일별 수정 여부, 파일 트리 메타데이터**의 주인은 Zustand다.
- 같은 정보를 두 곳에 복제하지 않는다. 다른 레이어에 탭 정보가 필요하면 dockview 이벤트를 business hook에서 받아 쓴다.

## 결과

- 그룹 크기가 바뀔 때마다 Monaco `layout()`을 다시 불러야 한다. `ResizeObserver`로 처리하고, 연속 리사이즈는 프레임 단위로 묶는다.
- 그룹 사이 포커스 이동, 탭 끌어 놓기, 레이아웃 저장·복원을 테스트해야 한다.
- dockview 번들 크기를 측정해 README의 번들 분석에 포함한다.
- 기본 화면은 기본 레이아웃을 그대로 지킨다.
