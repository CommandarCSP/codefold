# ADR-0011. 기능 브랜치 + `--no-ff` 병합, Conventional Commits(설명은 한국어)를 쓴다

- 상태: 승인 (커밋 범위 이름은 ADR-0023으로 일부 대체)
- 날짜: 2026-09-27

## 배경

커밋 기록은 코드만큼 중요한 문서다. 히스토리를 읽는 사람이 기능 단위로 변경을 따라갈 수 있어야 하고, 커밋마다 의도가 분명해야 한다.

## 결정

### 브랜치

- 기능마다 최신 `origin/main`에서 `<type>/<짧은-설명>` 브랜치를 만든다.
- 끝나면 최신 `main` 위로 rebase하고 `--no-ff` merge commit(`merge: <기능 설명>`)으로 합친다. 기능을 이루는 커밋을 모두 남기면서도 `git log --graph`에서 기능 단위로 묶어 볼 수 있다. fast-forward·squash와의 비교는 README "왜 rebase 후 `--no-ff`로 병합하나요?"에 정리한다.
- `main`에는 force push하지 않는다.

### 커밋 메시지

- Conventional Commits 형식을 따른다. 타입: `feat`, `fix`, `perf`, `refactor`, `test`, `docs`, `chore`. 범위: `zip`, `file-kind`, `editor`, `web`, `repo`, `adr`.
- 타입과 범위는 영어, **설명과 본문은 한국어**로 쓴다.

| 선택지 | 판단 |
|---|---|
| A. 키워드는 영어, 설명은 한국어 | **채택.** 문서와 ADR이 한국어라 일관되고, 커밋 종류는 Conventional Commits 키워드로 그대로 검색된다 |
| B. 전부 영어 | 오픈소스 관례에 가깝지만 이 프로젝트의 문서 언어와 맞지 않는다 |

- 한 커밋에는 한 가지 의도만 담는다.
- 테스트는 그 테스트가 검증하는 구현과 같은 커밋에 둔다. 어느 커밋에서도 테스트가 통과해야 한다.
- 설계 결정을 반영한 커밋은 본문에 `Refs: ADR-NNNN`을 적는다.

타입별 의미와 예시는 README의 "커밋 메시지" 절에 표로 정리한다.

## 결과

- 히스토리가 "기능 → 그 기능을 이루는 작은 커밋들" 구조가 되어 리뷰와 되돌리기가 쉽다.
- 커밋에서 ADR로, ADR에서 커밋으로 근거를 추적할 수 있다.
