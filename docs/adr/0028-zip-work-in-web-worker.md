# ADR-0028. ZIP 읽기·압축 해제·재압축은 Web Worker에서 한다

- 상태: 승인
- 날짜: 2026-09-27
- 보완: ADR-0001, ADR-0016

## 배경

ADR-0001에서 ZIP을 직접 파싱하고, 처음에는 파일 목록(Central Directory)만 읽기로 했다. 목록을 읽는 시간은 항목 수에 비례한다. 1만 개가 넘는 ZIP에서는 항목마다 헤더를 읽고 파일 이름을 디코딩하는 일이 수십~수백 ms 걸릴 수 있다(측정 전 추정). 압축 해제와 다운로드용 재압축도 파일이 크면 시간이 든다.

이 일을 메인 스레드에서 하면 그동안 화면이 멈춘다. ADR-0027은 입력 중에 50ms를 넘는 긴 작업을 0건으로 목표를 잡았다. ADR-0016은 모든 읽기 함수를 비동기로 만들어 Worker 안에서 구현해도 호출하는 쪽이 바뀌지 않게 했다.

## 선택지

ZIP 작업을 어느 스레드에서 할지 두 가지를 비교했다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. Web Worker에서 한다 | 큰 ZIP의 목록을 읽거나 내려받을 ZIP을 만드는 동안에도 화면과 입력이 멈추지 않는다 | 메인 스레드와 Worker 사이에 메시지를 주고받는 코드가 필요하다 |
| B. 메인 스레드에서 한다 | 코드가 단순하다 | 큰 ZIP에서 화면이 멈추고 긴 작업 0건 목표(ADR-0027)를 지키기 어렵다 |

## 결정

**A를 택한다.**

### 역할 나누기

- `zip-archive` 패키지 자체는 스레드를 모른다. 앱이 Worker 안에서 `zip-archive`를 쓴다.
- 메인 스레드에는 Worker를 부르는 비동기 대리 객체를 둔다. 이 객체는 두 가지를 제공한다.
  - **파일 출처**: `FileSource` 모양(목록, 앞부분 읽기, 전체 읽기)이라 `virtual-fs`에 그대로 넘긴다(ADR-0016).
  - **ZIP 만들기**: `exportZip(내보내기 계획, 수정된 파일 내용)`을 부르면 Worker가 결과 ZIP을 만들어 `Blob` 하나로 돌려준다. 안 바뀐 파일의 원본 압축 바이트는 Worker 안에서만 복사되고 메인 스레드로 넘어오지 않는다.
- 압축 해제(`DecompressionStream`)와 재압축(`CompressionStream`)도 Worker에서 한다.
- 메인 스레드와 Worker의 메시지 형식은 `apps/zip-editor`의 services 계층 한 곳에 둔다.

### 데이터를 넘기는 방법

- 업로드한 파일(`Blob`)을 `postMessage`로 넘기면 객체만 복제되고 안의 바이트는 복사되지 않는다. 브라우저가 밑바탕 데이터를 공유하기 때문이다. 그래서 큰 ZIP도 메모리를 두 벌 쓰지 않는다. `Blob`은 transfer 대상이 아니다. Worker는 `Blob.slice()`로 필요한 범위만 읽는다.
- Worker가 돌려주는 항목 목록은 순수 객체다(ADR-0017).
- 파일 바이트는 `Uint8Array`가 가리키는 `ArrayBuffer`를 transfer 목록에 넣어 복사 없이 넘긴다. `subarray()`로 만든 조각을 넘기면 버퍼 전체가 넘어가고 Worker 쪽 버퍼는 분리(detach)되므로, 넘길 조각은 버퍼를 따로 가지게 만든다.

## 결과

- 1만 개가 넘는 ZIP의 목록을 읽거나 내려받을 ZIP을 만드는 동안에도 입력과 화면이 멈추지 않는다.
- 받은 목록을 메인 스레드에서 풀고 `virtual-fs`가 트리를 만드는 일은 메인 스레드에 남는다. 이 시간은 ADR-0027의 "1만 개 트리 1초" 지표로 재고, 목표를 넘으면 트리 만들기도 Worker로 옮기는 것을 검토한다.
- Worker 메시지 코드와 그 테스트가 늘어난다. `zip-archive` 패키지의 단위 테스트는 Worker 없이 그대로 돈다.
- Worker 파일은 Vite의 `?worker` import로 번들한다.
