# ADR-0027. 성능 목표를 숫자로 정하고, CI에서 계속 잰다

- 상태: 승인 (렌더 횟수 검사 방법은 ADR-0045로 일부 대체)
- 날짜: 2026-09-27

## 배경

코드 에디터에서 성능은 기능만큼 중요하다(빠른 입력 중의 반응성, 불필요한 렌더, 번들 크기, 파일이 많은 ZIP). 목표 숫자가 없으면 "빠르다"를 증명할 기준이 없고, 구현하면서 조금씩 느려져도 알아채기 어렵다. 구현을 다 마친 뒤 한 번만 재면 같은 문제가 남으므로, 구현하는 동안 계속 재야 한다.

## 선택지

목표를 둘지, 둔다면 어떻게 지킬지를 두고 세 가지 방법을 비교했다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 목표 숫자를 정하고 CI에서 계속 잰다 | 기준을 넘으면 CI에서 바로 드러난다. 결과를 숫자로 설명할 수 있다 | 측정 스크립트를 만들어야 한다 |
| B. 목표 없이 측정해 기록만 한다 | 준비할 것이 적다 | 느려져도 알아채기 어렵다 |
| C. 목표를 두되 구현을 마친 뒤 한 번만 잰다 | 단순하다 | 구현 중에 목표를 넘어도 모른다 |

## 결정

**A를 택한다.**

### 목표와 검사 방법

지표마다 목표와 검사 방법, CI에서 어떻게 처리할지를 정한다.

| 지표 | 목표 | 검사 방법 | CI 처리 | 근거 |
|---|---|---|---|---|
| 첫 화면 JS 크기 | gzip 150KB 이하 | 빌드 결과를 재는 스크립트 | 넘으면 실패 | ADR-0013, ADR-0021 |
| 키 입력당 React 렌더 | 0회 (단, 파일이 처음 수정될 때는 1회) | React `<Profiler>`로 커밋 횟수를 세는 테스트 페이지에서 Playwright로 100글자를 입력한 뒤 횟수 확인 | 넘으면 실패 | ADR-0006, ADR-0019 |
| 1만 개 파일 ZIP의 트리 표시 | 올린 뒤 1초 이내 | Playwright와 `performance.mark`로 측정 | 결과를 기록하고, 넘으면 경고 | ADR-0001, ADR-0016 |
| 입력 중 긴 작업 | 50ms를 넘는 작업 0건 | Long Tasks API(`PerformanceObserver`)로 측정 | 결과를 기록하고, 넘으면 경고 | ADR-0006 |

- **렌더 횟수는 실패 조건으로 둔다.** 기기 속도와 상관없이 늘 같은 값이 나오기 때문이다.
- **시간 지표는 경고만 한다.** CI 러너는 실행할 때마다 속도가 들쭉날쭉해서, 실패 조건으로 두면 코드와 상관없이 CI가 깨질 수 있다. 결과는 CI 산출물로 남겨 추세를 본다.
- **기준 환경**은 GitHub Actions `ubuntu-latest` 러너의 Chromium이다. 누구나 같은 환경에서 다시 잴 수 있다. 개발 기기에서 잰 값은 참고값으로 따로 적는다.
- **50ms 기준**: 사용자는 입력에 100ms 안에 반응하면 즉각적이라고 느낀다(RAIL 모델). 100ms 안에 반응하려면 한 번에 도는 작업을 50ms 이하로 끊어야 한다. 브라우저도 50ms를 넘는 작업을 긴 작업(long task)으로 분류한다.
- 성능 측정은 그 기능이 생긴 때부터 CI에 붙인다. 예를 들어 트리 표시 측정은 파일 트리를 구현하면서 추가한다.

### 첫 화면 번들에서 빼는 것

첫 화면에는 업로드 영역만 보인다. 에디터 영역은 ZIP을 연 뒤에야 필요하므로, 다음은 첫 화면 번들에서 뺀다. ZIP 열기나 복원을 시작할 때 동적 import를 시작해, 내려받는 시간이 ZIP 파일 목록을 읽는 시간과 겹치게 한다.

- Monaco (ADR-0021)
- dockview (ADR-0007). 에디터 영역과 함께 불러온다.

이 두 청크와 언어별 청크의 크기는 목표 없이 측정해 기록한다. Monaco 청크에서 조정할 수 있는 것은 어떤 언어를 등록하고 언제 불러올지(ADR-0026)뿐이다.

### 성능 리포트

지표마다 목표, 측정 방법, 측정 환경, 결과, 관련 ADR을 적은 성능 리포트 문서를 따로 둔다. CI 측정값을 바탕으로 품질 마무리 단계에서 정리하고, README에는 요약만 싣는다.

## 결과

- 첫 화면 번들이 목표를 넘거나 키 입력마다 렌더가 일어나면 CI가 실패한다.
- 시간 지표는 구현하는 동안 계속 기록되어, 느려지는 시점을 추세로 찾을 수 있다.
- 목표를 넘는 결과가 나오면 원인과 대응을 성능 리포트에 기록한다.
