# ADR-0001. ZIP 파서를 직접 구현한다

- 상태: 승인 (파일 이름 읽는 순서는 ADR-0037로 일부 대체)
- 날짜: 2026-09-27

## 배경

ZIP을 열어 파일 트리를 만드는 코드를 어디까지 직접 작성할지 정해야 한다. 범위는 두 가지로 잡을 수 있다.

1. ZIP 파일 형식(바이트 구조)을 읽는 코드까지 직접 작성한다.
2. 압축 해제는 라이브러리에 맡기고, 파일 목록을 트리로 바꾸는 코드만 직접 작성한다.

또한 파일이 1만 개가 넘는 ZIP에서도 빠르게 동작해야 한다(선택 요구사항).

## 선택지

요구사항을 어떻게 읽느냐에 따라 세 가지 방법이 나온다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. ZIP 구조를 직접 파싱하고, deflate 해제는 브라우저 내장 `DecompressionStream` 사용 | 요구사항 문구를 그대로 충족한다. ZIP 라이브러리 의존성이 없다. 필요한 파일만 골라 해제하는 등 성능 최적화를 마음대로 설계할 수 있다 | 구현량이 많다. 형식의 예외 상황을 직접 처리해야 한다 |
| B. JSZip/fflate로 해제하고 트리 변환만 직접 작성 | 빠르고 검증된 구현이다 | "파싱을 직접 작성"하라는 조건을 문구 그대로는 충족하지 못한다. 라이브러리가 정한 방식(보통 전체 해제) 밖으로 최적화하기 어렵다 |
| C. ZIP 구조는 직접 파싱하고 deflate 알고리즘만 fflate 사용 | 브라우저 호환성 걱정이 적다 | 현재 지원 대상 브라우저는 모두 `DecompressionStream`을 지원하므로 이득이 작다 |

## 결정

**A를 택한다.** ZIP의 End of Central Directory(EOCD)와 Central Directory를 직접 읽어 파일 목록을 만들고, 각 파일의 Local File Header를 따라가 압축 데이터를 꺼낸다. 압축 해제와 재압축은 브라우저 내장 `DecompressionStream('deflate-raw')` / `CompressionStream('deflate-raw')`을 쓴다.

지원 범위는 다음과 같다.

- 압축 방식: Stored(0), Deflate(8)
- **ZIP64 읽기 지원**: 원래 ZIP 형식은 파일 크기·위치를 4바이트, 파일 개수를 2바이트 칸에 적기 때문에 약 4GB, 65,535개가 한도다. 이 한도를 넘는 ZIP이나, 일부 압축 프로그램이 작은 ZIP에도 ZIP64 기록을 붙인 경우에 대비해 ZIP64 EOCD 레코드와 확장 필드(0x0001)를 읽는다.
- 파일 이름 인코딩: UTF-8 플래그(general purpose bit 11)가 있으면 UTF-8로 읽는다. 플래그가 없으면 먼저 UTF-8로 엄격하게 읽어 본다(플래그 없이 UTF-8로 쓰는 도구가 많다). 실패하면 CP949로, 그것도 깨지면 CP437로 읽는다. CP437은 브라우저 `TextDecoder`가 지원하지 않으므로 128자 변환표를 직접 둔다.
- **범위 밖**: 암호화된 ZIP, 여러 파일로 나뉜 분할 ZIP.

## 결과

이 결정으로 얻는 것과 떠안는 것은 다음과 같다.

- **사용자가 연 파일만 압축을 해제**할 수 있다. 처음 열 때는 파일 목록만 읽고 압축은 풀지 않는다. 여는 시간은 항목 수에 비례하지만 항목마다 헤더 하나(46바이트 + 파일 이름)만 읽으므로, 전체 데이터 크기와는 상관이 없다.
- 다운로드할 때 **바뀌지 않은 파일은 다시 압축하지 않고 원래 압축 바이트를 그대로 복사**할 수 있다. 수정한 파일만 새로 압축한다.
- ZIP 라이브러리가 번들에 들어가지 않는다.
- 형식의 예외 상황(폴더 항목이 없는 ZIP, `__MACOSX` 같은 부가 파일, 손상된 헤더 등)은 직접 테스트로 지켜야 한다. 실제 압축 프로그램(macOS Finder, Windows 탐색기, `zip` CLI 등)으로 만든 샘플 ZIP을 테스트 자료로 둔다.
- 4GB가 넘는 ZIP은 형식상으로는 읽을 수 있지만, 브라우저 메모리 한계 때문에 실제 편집은 보장하지 않는다.
