# ADR-0041. 원본 ZIP은 별도 저장소에 두고, 저장본에 작업 공간 id를 붙인다

- 상태: 승인
- 날짜: 2026-09-28
- 보충: ADR-0014

## 배경

ADR-0014는 작업 상태를 IndexedDB에 자동 저장하고, ZIP 원본(Blob)은 업로드할 때 한 번 저장한다고 정했다. 구현하며 두 문제가 드러났다.

- 원본 ZIP을 작업 공간 기록 안에 두면, 자동 저장이 기록을 읽고 다시 쓸 때마다 ZIP 전체를 읽고 쓴다. 50MB ZIP에서 저장 한 번에 메인 스레드가 약 13ms 멈췄고, 멈추는 시간은 ZIP 크기에 비례해 늘었다. 그런데 이 앱은 1GB가 넘는 ZIP도 경고를 보인 뒤 연다.
- 새 ZIP의 저장이 실패하면(용량 초과 등) 옛 ZIP의 기록이 남는다. 그 뒤 자동 저장이 새 ZIP의 편집을 옛 기록에 섞고 "저장됨"을 보였다.

또 Playwright로 띄운 WebKit에서는 IndexedDB에 Blob을 넣으면 오류 내용 없이 쓰기가 실패했다.

## 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 원본 ZIP을 별도 저장소(`zip`)에 두고 업로드할 때만 쓴다. 작업 공간 기록에는 메타데이터만 둔다. 기록마다 작업 공간 id를 붙이고, id가 다르면 저장하지 않는다 | 자동 저장이 ZIP을 건드리지 않는다. 다른 ZIP의 기록에 편집이 섞이지 않는다 | DB 버전을 올리고 옛 형식을 옮겨야 한다 |
| B. 지금처럼 기록 하나에 두고, 저장할 때 ZIP만 빼고 고친다 | 저장소가 늘지 않는다 | IndexedDB는 값 일부만 고칠 수 없어, 기록을 쓰면 ZIP도 함께 다시 쓴다 |

## 결정

**A를 택한다.**

- DB 버전 2에서 저장소는 `workspace`(메타데이터), `files`(고친 파일 내용), `zip`(원본 ZIP) 셋이다. DB를 버전 2로 올릴 때 버전 1 기록 안의 원본 ZIP을 `zip` 저장소로 옮긴다.
- 새 ZIP을 저장할 때마다 작업 공간 id를 새로 만든다. 자동 저장은 지금 작업 공간의 id와 저장된 기록의 id가 다르면 쓰지 않는다.
- 새 ZIP 저장이 실패하면 저장본을 지우고(지울 수 있으면), 그 작업 공간에는 자동 저장을 붙이지 않는다. 저장 불가 배너가 남는다.
- 원본 ZIP은 Blob 그대로 넣는다. 처음 저장할 때 작은 Blob을 넣어 보고, 브라우저가 Blob을 받지 못하면 바이트와 MIME 형식으로 넣는다.

## 근거

- 원본 ZIP은 업로드할 때 한 번만 바뀐다. 자주 바뀌는 기록과 저장소를 나누면, 자동 저장 비용이 ZIP 크기와 상관없어진다.
- id를 붙이면 저장본과 작업 공간이 어긋났을 때 편집이 조용히 섞이지 않고, 저장이 실패해 드러난다.
- Blob을 넣지 못하는 브라우저만 바이트로 넣으면, 다른 브라우저는 ZIP을 메모리로 읽어 들이지 않는다.

## 결과

- 저장소 테스트는 세 가지를 확인한다. `save`와 `readSummary`가 `zip` 저장소를 읽지도 쓰지도 않는지, 버전 1 형식 두 가지(Blob, 바이트)를 옮기는지, Blob을 넣지 못할 때 바이트로 넣는지다.
- 버전 1 코드를 연 탭이 남아 있으면, 새 탭은 그 탭이 닫힐 때까지 DB 버전을 올리지 못하고 멈출 수 있다. 버전 1은 배포된 적이 없어 지금은 처리하지 않는다. 배포한 뒤 DB 버전을 올릴 때는 `blocked`·`versionchange` 처리를 함께 넣는다.
