# ADR-0017. 공개 API는 interface와 팩토리 함수로, 데이터는 순수 객체로 만든다

- 상태: 승인
- 날짜: 2026-09-27

## 배경

ADR-0016에서 패키지끼리는 모양(인터페이스)만 알고 구현은 모르게 하기로 했다. 공개 API를 class로 만들지 팩토리 함수로 만들지, 데이터를 어떤 형태로 둘지 정해야 한다.

고려할 제약이 두 가지 있다.

- React에서는 `onClick={registry.close}`처럼 메서드를 콜백으로 넘기는 일이 많다. class 메서드는 이렇게 넘기면 `this`가 풀린다.
- ZIP 파싱 결과는 Web Worker에서 메인 스레드로 넘어오고, 작업 상태는 IndexedDB에 저장된다(ADR-0014). 두 경우 모두 브라우저가 structured clone으로 값을 복사하며, 이때 class 인스턴스의 프로토타입과 메서드는 사라지고 데이터만 남는다.

## 선택지

공개 API와 데이터의 형태에 따라 두 가지를 비교했다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 공개 API는 interface + 팩토리 함수, 데이터는 순수 객체 | `this`가 풀리지 않는다. 쓰는 쪽이 모양에만 의존한다. 클로저 변수는 실행 중에도 밖에서 접근할 수 없다. 데이터가 Worker와 IndexedDB를 오가도 깨지지 않는다 | 같은 객체를 아주 많이 만들면 메서드를 공유하지 않아 메모리를 더 쓴다 |
| B. 공개 API와 데이터 모두 class | 익숙한 객체지향 형태다. 메서드를 프로토타입으로 공유한다 | 콜백으로 넘길 때마다 `bind`가 필요하다. 데이터 인스턴스가 Worker·IndexedDB를 거치면 메서드가 사라진다 |

## 결정

**A를 택한다.** 대상별 규칙은 다음과 같다.

| 대상 | 방식 |
|---|---|
| 패키지 공개 API | `interface`와 `create…()` 팩토리 함수. 밖으로는 interface만 내보낸다 |
| 데이터(트리 노드, ZIP 항목, 내보내기 계획 등) | 메서드 없는 순수 객체와 `readonly` 타입 |
| 오류 | `class … extends Error`. `instanceof`로 종류를 구분해 ErrorBoundary와 `catch`에서 처리한다 |
| 상태가 많은 내부 구현 | 안쪽에서는 class를 써도 된다. 밖으로는 interface만 보인다 |
| 정리가 필요한 객체 | `dispose()`가 있는 `Disposable` 모양을 따른다. Monaco와 VS Code의 관례와 같다 |

A의 단점(메서드 비공유)은 이 프로젝트에서 문제가 되지 않는다. 팩토리로 만드는 객체는 model 관리자, workspace, 에디터 화면처럼 몇 개뿐이다. 수만 개가 생길 수 있는 트리 노드는 메서드 없는 순수 객체다.

## 결과

- 공개 API를 콜백으로 그대로 넘길 수 있다.
- 테스트에서 interface를 만족하는 가짜 구현을 쉽게 넣을 수 있다.
- 데이터 타입은 Worker 메시지와 IndexedDB 저장 형식으로 그대로 쓸 수 있다.
- 오류 종류는 class 계층으로 정의하고, 패키지마다 자기 오류 타입을 내보낸다.
